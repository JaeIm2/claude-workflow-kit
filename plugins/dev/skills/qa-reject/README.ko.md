# qa-reject — QA에서 반려된 작업 처리

[English](README.md) | 한국어

QA에서 반려(reject)된 작업을 처리하는 Claude Code 스킬. 업무 관리 도구에서 최신 반려 사유를 읽고, 사실은 다른 사람 변경이 원인인지 확인하고, 작업 기록에서 원래 브랜치를 찾아 문제를 재현하고 고친다. 그다음 재이관 준비까지 한다: 커밋, 그리고 승인 후 push, 배포 확인, 업무 관리 도구 댓글과 상태 변경.

**언제 쓰나:** QA에서 작업이 반려돼서, 사유 확인부터 재현, 수정, 재전달까지 처리해야 할 때.

**이렇게 말해보기:**
- "PROJ-123 QA에서 까임"
- "reject 먹었다"
- "reject 사유 확인하고 수정해줘"

**준비물:** git. 업무 관리 도구 연결은 선택 (없으면 QA 댓글을 붙여넣으면 된다).

## 필요한 것
- Claude Code, git
- (선택) 업무 관리 도구의 MCP 서버나 커넥터. 없으면 QA 댓글을 붙여넣으면 된다
- `/dev:task-start`, `/dev:task-finish`와 같이 쓰면 가장 좋다. 이 스킬이 읽는 작업 기록을 그쪽에서 남긴다

## 설치
1. Claude Code에서 아래 두 줄 실행 (자세한 설치 방법은 [루트 README](../../../../README.ko.md))
   ```
   /plugin marketplace add JaeIm2/claude-workflow-kit
   /plugin install dev@claude-workflow-kit
   ```
2. 작업이 반려되면 `/dev:qa-reject PROJ-123` 입력, 또는 "PROJ-123 QA에서 까임"이라고 말하기
3. 설정이 비어 있으면 `/dev:task-start`와 같은 질문을 한다 (빠진 것만). 바꾸고 싶으면 `/dev:task-start 설정`.

## 쓰는 법
- `/dev:qa-reject PROJ-123`, "reject 먹었다", "reject 사유 확인하고 수정해줘"

지키는 규칙:
- 최신 반려 사유만 본다. 이미 해결된 예전 지적에 끌려가지 않는다
- 내 변경이 원인이라고 단정하기 전에 해당 파일의 최근 이력을 확인하고, 다른 사람 작업을 건드려야 하면 먼저 알린다
- 사유가 불명확하면 추측으로 고치지 않고 QA에게 물어볼 질문 초안을 만든다
- 이미 머지된 브랜치면 기본 브랜치에서 새 수정 브랜치를 만든다. task-start와 같은 안전 확인을 거친다
- 커밋 전 빌드, push는 승인 후에만, QA 재이관은 수정이 테스트 환경에 배포된 걸 확인한 뒤에만
- 테스트 계정 정보는 저장하지 않는다

반려 사유와 수정 내용은 작업 기록에 추가된다. 같은 사유로 또 반려되면 그 기록이 근거가 된다.
